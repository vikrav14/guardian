# V52 Device: Specs, Capabilities & Integration

**Last updated:** 2026-07-29

The **ReachFar V52** is the latest model in Guardian's supported GPS pendant family, introducing advanced health monitoring, offline data buffering, and fall detection compared to the older V28C. This document covers V52 specifications, supported features, command compatibility, and real-world deployment considerations.

## Supported Features & Capabilities

### 1. GPS Location Tracking

**Status:** Verified on real hardware ✓

- **Primary:** Satellite GPS (high accuracy, ~5–10 m)
- **Fallback 1:** WiFi triangulation (via Google Geolocation API, ~50–100 m)
- **Fallback 2:** Cell tower triangulation LBS (via Google Geolocation API, ~200–400 m)
- **Upload Frequency:** Every 30–3600 seconds (configurable via `UPLOAD` command)
- **Packet Type:** `UD_LTE` (LTE variants: `UD_WCDMA`, `UD_GPS` handled identically)

**Gateway Integration:**
- Parses UD/UD_LTE with location validity flag (A=satellite GPS, V=WiFi/LBS)
- Geolocation triggered for V packets when `GOOGLE_GEOLOCATION_API_KEY` is set
- Evaluates geofences in real-time (even during offline periods, once reconnected)
- Writes location history to Firestore (if `WRITE_LOCATION_HISTORY=true`)

**Code reference:** `gateway/src/protocol/gt06.js`, lines 39–128 (parseLocationData)

---

### 2. Fall Detection

**Status:** Designed & tested (vendor doc confirmed, real hardware TBD)

- **Detection Method:** Accelerometer + machine learning (vendor proprietary)
- **Sensitivity Levels:** 0 (least sensitive) to 6 (most sensitive)
- **Response Options:**
  - Alert only (wearer is notified)
  - Auto-dial (device calls emergency contact if not acknowledged within 30 seconds)
- **False Positive Rate:** Not quantified by vendor; real-world testing recommended
- **Trigger Packet:** `AL` alarm with bit 21 set (`0x00200000`)

**Supported Commands:**
| Command | Type | Syntax | Required | Notes |
|---------|------|--------|----------|-------|
| Enable/Disable | TCP downlink | `FALLDOWN,enabled,dialOnFall` | Yes | `enabled=1/0`, `dialOnFall=1/0` |
| Set Sensitivity | TCP downlink | `LSSET,level+6` | Yes | Level 0–6; second parameter always 6 (vendor constant) |

**Guardian Implementation:**
- Falls are reported as critical-severity alerts
- Trigger SMS/WhatsApp to emergency contacts (not just push to caregiver)
- Device state cached in Firestore: `devices/{imei}.fallDetection` and `fallDetectionSensitivity`
  - Note: No "read-back" command exists; cache is best-effort
- App allows guardians to enable/disable and adjust sensitivity

**Code reference:** `gateway/src/commands.js`, lines 67–83

**Unverified Caveat:**
Fall detection has been **tested against vendor docs** but not yet validated on real V52 hardware in Mauritius. Community testing or a vendor site visit recommended before production deployment.

### 3. Health Monitoring

**Status:** Designed (unverified on real hardware)

#### 3a. SpO2 (Blood Oxygen)

- **Measurement:** Percentage (typically 95–100)
- **Trigger:** Device sends SpO2 reading when requested (e.g., via smartwatch UI)
- **Packet Type:** `oxygen`
- **Payload:** `oxygen,oxyType,oxyValue` (e.g., `oxygen,0,98`)

**Gateway Action:**
1. Parse SpO2 value
2. Send ACK: `[SG*<protocolId>*0008*oxygen,1]` (1 = success, 2 = error)
3. Store in Firestore under a future `health_readings/{id}` collection

**Status in App:** Currently logged but not displayed (no UI yet). See GitHub issue #XX for feature status.

**Code reference:** `gateway/src/protocol/gt06.js`, lines 272–287

#### 3b. Heart Rate + Blood Pressure

- **Measurements:** Systolic (mmHg), Diastolic (mmHg), Heart Rate (BPM)
- **Trigger:** Device responds after `hrtstart` command sent
- **Packet Type:** `bphrt`
- **Payload:** `bphrt,systolic,diastolic,heartRate[,trailing fields]`

**Example:**
```
[3G*9705314117*0010*bphrt,120,72,72,,,,]
└─ Systolic: 120 mmHg, Diastolic: 72 mmHg, HR: 72 BPM
```

**Gateway Action:**
1. Parse first three fields (systolic, diastolic, HR)
2. Trailing fields are present in vendor examples but undocumented; left unparsed
3. Send ACK: `[SG*<protocolId>*0005*bphrt]`
4. Store in Firestore under `health_readings/{id}`

**Status in App:** Currently logged but not displayed (no UI yet).

**Code reference:** `gateway/src/protocol/gt06.js`, lines 287–306

**Unverified:** Only the three documented fields are parsed. Trailing fields present in vendor examples remain unknown.

### 4. Medication Reminders

**Status:** Designed (unverified on real hardware)

Scheduled medication alerts via wearable display + optional sound/vibration.

**Supported Frequencies:**
- Once (one-time reminder)
- Daily (same time every day)
- Weekly (custom day mask, e.g., weekdays only)

**Command:** TCP downlink only (no SMS equivalent)

**Syntax:**
```
TAKEPILLS,HH:MM-enabled-frequency[-weekMask],frequency,hex-UTF16-text

HH:MM        = Time of day (24-hour format, e.g., 09:30)
enabled      = 1 (on) or 0 (off)
frequency    = 1 (once) | 2 (daily) | 3 (weekly)
weekMask     = "7-digit Sun->Sat on/off mask" (required only when frequency=3)
hex-UTF16-text = Reminder text encoded as UTF-16BE hex (4 hex chars per character)
```

**Examples:**

*Once, at 14:00, text "Take insulin"*
```
TAKEPILLS,14:00-1-1,1,0054006100690065002000690067006e0075006c0069006e
```

*Daily, at 09:30, text "Aspirin"*
```
TAKEPILLS,09:30-1-2,2,00410073007000690072006900690066
```

*Weekly (Mon-Fri), at 10:00, text "Vitamin D"*
```
TAKEPILLS,10:00-1-3-0111110,3,0056006900740061006d0069006e002000440000
```

**Gateway Implementation:**
- Medication reminders stored in Firestore at `medicationReminders/{reminderId}`
- App displays list, allows guardian to add/edit/remove
- Changes trigger a new `deviceCommands` entry so pendant stays in sync
- Text is auto-encoded to hex-UTF16 by `textToHexUtf16()` function

**Code reference:** `gateway/src/commands.js`, lines 48–122

**Unverified:** Never tested on real hardware. The hex-UTF16 encoding is confirmed via vendor example captures ("daily" → `006400610069006c0079`), but end-to-end setup has not been validated.

### 5. Blind-Spot Re-Upload (UD2)

**Status:** Designed (unverified on real hardware)

The V52's most significant advantage: when the device reconnects after losing signal, it replays buffered location history (up to 7 days). Guardian reconstructs the full journey.

**Packet Type:** `UD2` (V28C and V46/V48 do not send this)

**Payload Format:** Identical to `UD_LTE`, but multiple packets in sequence
```
UD2,DDMMYY,HHMMSS,A,lat,latDir,lng,lngDir,speed,course
UD2,DDMMYY,HHMMSS,A,lat,latDir,lng,lngDir,speed,course
UD2,DDMMYY,HHMMSS,A,lat,latDir,lng,lngDir,speed,course
```

**Key Difference from UD:**
- **No ACK sent** — Vendor spec: "Server no need reply"
- **Marked as blind-spot reupload** in Firestore for audit/replay

**Gateway Action:**
1. Parse each UD2 packet as a normal location update
2. Mark with `blindSpotReupload: true` in event metadata
3. Reconstruct polyline journey from buffered points
4. Display full route history in mobile app

**Benefits:**
- No lost location data during service interruptions
- Complete journey replay (not just current position)
- Offline periods become visible on the map

**Gateway Integration:**
- Locations flagged as blind-spot re-upload are stored to `devices/{imei}/journeys/{id}` as a single polyline-compressed segment
- App shows these segments with visual indication they are reupload data, not live tracking

**Code reference:** `gateway/src/protocol/gt06.js`, lines 238–254

**Unverified:** Not yet tested on real hardware. Offline buffering capacity (7-day estimate) not verified against actual pendant behavior.

### 6. Heartbeat & Battery Monitoring

**Status:** Verified on real hardware ✓

- **Packet Type:** `LK` (Link Keep-Alive)
- **Frequency:** Every 30–3600 seconds (configurable)
- **Payload:** `LK,steps,rolls,battery`
  - `steps` = Step count (V52 pedometer; V28C always sends 0)
  - `rolls` = Fall events detected (V52 only; V28C always sends 0)
  - `battery` = 0–100 (integer percentage)

**Example:**
```
[3G*9705314117*000B*LK,142,0,78]
└─ 142 steps, 0 falls detected, 78% battery
```

**Gateway Action:**
1. Extract battery percentage
2. Send ACK: `[SG*<protocolId>*0002*LK]`
3. Update `devices/{imei}.batteryPercent`
4. Update `devices/{imei}.lastHeartbeatAt` timestamp
5. Mark device as `online: true`

**Low Battery Alert:** When battery drops ≤ 15%, device sends `AL` with bit 17 set (low battery alarm). Gateway creates alert and notifies caregiver + emergency contacts.

**Code reference:** `gateway/src/protocol/gt06.js`, lines 233–237

### 7. Configurable Upload Interval

**Status:** Designed (unverified on real hardware)

Set standing GPS location reporting frequency, balancing accuracy and battery life.

**Command:** TCP downlink only
```
UPLOAD,<seconds>
```

**Constraints:**
- Minimum: 10 seconds
- Maximum: 3600 seconds (1 hour)

**Examples:**
```
UPLOAD,60     # Send location every 60 seconds
UPLOAD,300    # Send location every 5 minutes
UPLOAD,3600   # Send location every hour
```

**Gateway Implementation:**
- App provides slider (10s–1h) for guardian to adjust
- Sending the command requires an active TCP session
- Cached in Firestore at `devices/{imei}.locationReportingIntervalSeconds` (best-effort cache; no read-back command exists)

**Code reference:** `gateway/src/commands.js`, lines 124–137

**Unverified:** Not yet tested on real hardware.

## Verified vs. Designed Features

Guardian maintains a distinction between features that have been tested on real hardware and those documented by the vendor but not yet validated:

### Verified (✓)

- **GPS location tracking** — Tested against real V28C, V46, V48 in Mauritius
- **Geofencing** — Smart zones evaluated in real-world deployments
- **Heartbeat + battery** — LK packets confirmed in production
- **SOS button** — AL packets with bit 16 verified
- **Offline TCP recovery** — Device TCP reconnection behavior observed

### Designed (🔨)

- **Fall detection** — Vendor docs confirm `FALLDOWN`/`LSSET` commands, but never tested on V52 hardware
- **Health monitoring** — `oxygen`, `bphrt` packets documented; parsing confirmed against vendor examples; no real-world validation
- **Medication reminders** — `TAKEPILLS` command confirmed in vendor examples; never tested end-to-end
- **Blind-spot re-upload (UD2)** — Documented in V46-V48-V52 protocol; never observed in practice
- **Configurable upload interval** — TCP `UPLOAD` command vendor-documented; untested on V52

### Unverified (❌)

- **Voice monitoring** (`monitor`) — RF-V28 community source; not in official V52 docs
- **Ring to find** (`find`) — RF-V28 community source; not in official V52 docs
- **Remote photo capture** — Mentioned in some forums; no command syntax or protocol format found anywhere
- **Pedometer / step counting** — Device sends step counts in LK, but end-to-end app display never tested
- **Body temperature readings** — Referred to in some protocol docs; no parsing logic implemented

## Setup Walkthrough (V52)

Setup is nearly identical to V28C, except V52 uses TCP downlink instead of SMS for advanced commands.

### Prerequisites

| Item | Notes |
|------|-------|
| V52 pendant | IMEI on label or in device settings |
| my.t SIM | SMS + mobile data active; note the pendant's SIM phone number (E.164, e.g. `+23058590100`) |
| PC running gateway | `cd gateway && npm start` (listens on TCP port 9000) |
| ngrok TCP tunnel | `ngrok tcp 9000` (for local testing; production needs real hosting) |
| Firebase project | `FIRESTORE_DISABLED=false` in `gateway/.env` |

### Part A — Gateway Setup

1. Configure `gateway/.env`:
```env
PORT=9000
HOST=0.0.0.0
FIRESTORE_DISABLED=false
FIREBASE_PROJECT_ID=your-project
GOOGLE_APPLICATION_CREDENTIALS=/path/to/serviceAccount.json
WRITE_LOCATION_HISTORY=true
GOOGLE_GEOLOCATION_API_KEY=your-key  # For WiFi/LBS fallback
```

2. Start gateway:
```bash
cd gateway
npm install
npm start
```

3. Expose TCP port with ngrok:
```bash
ngrok tcp 9000
# Output: tcp://8.tcp.ngrok.io:15375
```

4. Smoke-test with simulator:
```bash
npm run simulate
```

### Part B — Device Setup (SMS)

Unlike V52, V52 typically ships pre-configured for the vendor's cloud. To point it at your gateway:

1. **Set center number (callback):**
```text
pw,123456,center,+23058590100#
```

2. **Check status:**
```text
pw,123456,ts#
```
(Device replies with IMEI, network status, current server address)

3. **Configure APN** (if needed; device may auto-provision on my.t):
```text
pw,123456,apn,my.t,,,61701#
```

4. **Point device at your gateway:**
```text
ip,8.tcp.ngrok.io,15375#
```

5. **Verify status again:**
```text
pw,123456,ts#
```
(Should reflect your ngrok host/port within 1–5 minutes)

> **Important:** After each ngrok restart, the host/port changes. Re-send the `ip,...#` SMS.

### Part C — Link in Guardian App

1. Read **15-digit IMEI** from device label or status SMS reply
2. In Flutter app: **Account → Link a pendant**
3. Enter the IMEI and confirm
4. Gateway writes to Firestore; app displays device within 1–2 heartbeat intervals

### Part D — Test Features

#### GPS Tracking
- Confirm `location.lat` / `location.lng` appear in `devices/{imei}` after first UD_LTE
- Wait 5–10 minutes for first satellite GPS fix (may be faster if outdoors)

#### Fall Detection
- Open app: **Care Settings → Fall Detection**
- Toggle on/off → Confirm `devices/{imei}.fallDetection.enabled` updates in Firestore
- Adjust sensitivity → Confirm `fallDetectionSensitivity` changes

#### Health Readings
- Trigger heart rate on device (e.g., app button or device UI)
- Expect `bphrt` packet from device within 30 seconds
- Check Firestore: `health_readings/{id}` collection appears (once app UI is built)

#### Medication Reminders
- App: **Care Settings → Medications**
- Add reminder (e.g., "08:00 Daily: Take Aspirin")
- Confirm `medicationReminders/{id}` appears in Firestore
- Wait for scheduled time: device should vibrate/alert

#### Offline Buffering
- Take device offline (airplane mode or move out of signal)
- Let it sit for 10 minutes, then reconnect
- Expect UD2 packets replaying the offline period
- App journey view should show complete route (no gap)

## Troubleshooting

| Problem | Cause | Fix |
|---------|-------|-----|
| No TCP connection | Device can't reach ngrok host/port | Re-check `ip,...#` SMS; confirm ngrok still running |
| Lots of battery drain | Upload interval too aggressive | Increase `UPLOAD` interval via app (e.g., 300s instead of 60s) |
| Health readings not parsed | Device firmware too old | Check device firmware version; update if available |
| UD2 packets not appearing | Device was never offline, or offline < 2 min | Take device offline intentionally; wait > 5 min before reconnect |
| Fall detection not triggering | Sensitivity too low, or device not worn properly | Adjust `LSSET` to higher level (e.g., 5); ensure worn on wrist |
| App doesn't link device | IMEI mismatch or Firestore rules blocking | Verify 15-digit IMEI; check Firestore rules allow your UID |
